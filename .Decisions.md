# Hardware Architecture Decisions & Trade-offs

## Project Overview

This document records the major hardware architecture decisions, alternatives considered, trade-offs, and final choices made while developing **Version 1** of the discrete-component programmable logic fabric.

The objective is to build a real, physically programmable logic fabric using standard digital ICs, with an STM32 acting as the configuration controller.

Version 1 is intentionally **combinational**. Sequential logic, registers, and feedback are deferred to a later version.

---

## 1. Design Goals

The architecture was developed around these goals:

- Build an actual programmable logic fabric rather than simply programming an FPGA device.
- Use readily available digital ICs.
- Make the internal operation visible and understandable.
- Allow arbitrary Boolean functions through LUTs.
- Allow LUTs to be connected together through programmable routing.
- Avoid electrical contention in the programmable interconnect.
- Keep the architecture small enough to build, debug, and explain.
- Allow an STM32 to configure the fabric through a small serial interface.
- Eventually accept high-level Boolean/HDL-like commands and generate the hardware configuration automatically.

The architecture therefore prioritizes **clarity, determinism, modularity, and educational value** over commercial FPGA-like density.

# 3. LUT Architecture

## Decision

Use **four 3-input LUTs**:

```text
L0
L1
L2
L3
```

Each LUT implements any Boolean function of three variables.

A LUT with `N` inputs requires `2^N` truth-table bits:

| LUT inputs | Truth-table entries |
|---:|---:|
| 2 | 4 |
| 3 | 8 |
| 4 | 16 |
| 5 | 32 |

### Why 3 inputs?

A 3-input LUT requires only eight configuration bits and maps directly to an 8:1 multiplexer.

A 4-input LUT would require 16 entries and a substantially larger multiplexer structure.

### Trade-off

**Advantages**
- Small hardware.
- Direct mapping to an 8:1 MUX.
- Every 3-variable Boolean function is possible.
- Truth tables are easy to inspect and debug.

**Disadvantage**
- Functions involving more than three signals may require multiple LUTs.

For this prototype, composing multiple small LUTs was preferred over making each LUT larger.

---

# 4. 74HC151 as the LUT Core

## Alternatives considered

A LUT could theoretically be built from:

- Individual logic gates.
- Decoder + programmable storage.
- Multiplexer-based logic.
- A larger custom combinational network.

## Final decision

Use a **74HC151 8:1 multiplexer**.

The 74HC151 provides exactly the structure needed for a 3-input LUT:

```text
3 select inputs
8 data inputs
1 selected output
```

The LUT is therefore conceptually:

```text
                 Configuration bits
                 D7 D6 D5 D4 D3 D2 D1 D0
                  |  |  |  |  |  |  |  |
                  +--+--+--+--+--+--+--+
                              |
                         74HC151
                              |
                         LUT output
```

The three logical LUT inputs drive the select inputs.

### Why this choice?

A LUT is fundamentally a truth-table lookup. An 8:1 MUX performs exactly that lookup:

```text
ABC = 000 -> D0
ABC = 001 -> D1
ABC = 010 -> D2
ABC = 011 -> D3
ABC = 100 -> D4
ABC = 101 -> D5
ABC = 110 -> D6
ABC = 111 -> D7
```

This makes the physical implementation directly correspond to the mathematical definition of a LUT.

---

# 5. LUT Configuration Storage

## Decision

Use a **74HC373 latch** to hold the eight configuration bits associated with each LUT.

Each LUT therefore contains:

```text
8-bit configuration
        |
        v
74HC373
        |
        v
74HC151 8:1 MUX
        |
        v
LUT output
```

For four LUTs:

```text
4 × 8 = 32 LUT configuration bits
```

### Why not drive the LUT directly from STM32 GPIOs?

Direct GPIO control would consume many microcontroller pins and tightly couple the fabric to the STM32.

The intended architecture is:

```text
STM32
  |
  | serial configuration
  v
shift registers
  |
  v
configuration latches
  |
  v
LUT fabric
```

This keeps the controller interface small and makes the fabric independently understandable.

---

# 6. LUT Bit-Ordering Convention

A fixed truth-table convention was established early because it affects both hardware and compiler generation.

The select ordering is:

```text
S0 = A = least-significant select bit
S1 = B
S2 = C = most-significant select bit
```

Therefore:

```text
ABC = 000 -> D0
ABC = 001 -> D1
ABC = 010 -> D2
ABC = 011 -> D3
ABC = 100 -> D4
ABC = 101 -> D5
ABC = 110 -> D6
ABC = 111 -> D7
```

The configuration byte is represented as:

```text
D7 D6 D5 D4 D3 D2 D1 D0
```

Thus configuration bit `n` corresponds directly to `Dn`.

**No logical bit reversal is used.**

This convention is part of the compiler's truth-table generation algorithm.

---

# 7. Validated LUT Configuration Examples

Under the established logical convention:

| Function | Configuration |
|---|---:|
| `A & B & C` | `80H` |
| `A \| B \| C` | `FEH` |
| `A ^ B ^ C` | `96H` |
| XNOR | `69H` |
| Majority / Carry | `E8H` |
| `A & B` | `88H` |
| `A \| B` | `EEH` |
| `A ^ B` | `66H` |
| XNOR of A,B | `99H` |
| `A` | `AAH` |
| `B` | `CCH` |
| `C` | `F0H` |

For a function using fewer than three variables, the unused variable is duplicated across its two states.

For example:

```text
F = A & B
```

does not depend on C, so both `C=0` and `C=1` rows produce the same result.

---

# 8. Why Multiple LUTs?

A single 3-input LUT handles any three-variable function, but multiple LUTs allow larger logic networks.

Example:

```text
L0 = A & B
L1 = C & D
L2 = L0 ^ L1
```

Therefore:

```text
F = (A & B) ^ (C & D)
```

can be implemented using three LUTs even though it contains four external variables.

This demonstrates the fundamental purpose of programmable interconnect:

```text
External signals
      |
      +----> L0 ----+
      |             |
      +----> L1 ----+----> L2 ----> F
```

---

# 9. Number of LUTs: Why Four?

## Decision

Version 1 uses **four LUTs**.

This is a practical capacity/complexity compromise.

### Fewer LUTs

Advantages:
- Lower IC count.
- Simpler routing.
- Easier debugging.

Disadvantages:
- Quickly becomes too limited for useful multi-stage logic.

### More LUTs

Advantages:
- More logic capacity.
- More decomposition possibilities.

Disadvantages:
- More ICs and wiring.
- Larger configuration.
- More routing complexity.
- Harder debugging.

Four LUTs provides meaningful programmable capacity while remaining manageable as a discrete prototype.

---

# 10. Programmable Routing — First Approach: Tri-State Buffers

The first routing architecture considered was a network of **tri-state buffers**.

Conceptually:

```text
L0 ----[Tri-state]----+
L1 ----[Tri-state]----+----> LUT input
L2 ----[Tri-state]----+
L3 ----[Tri-state]----+
```

Only one source should be enabled at a time.

### Advantages

- Conceptually resembles a shared programmable bus.
- Can reduce the number of multiplexer structures.
- Demonstrates classical tri-state interconnect concepts.

### Problems / risks

If two sources are accidentally enabled:

```text
L0 ----> 1
L1 ----> 0
          |
          +---- shared node
```

the drivers contend.

This can produce:

- Undefined logic levels.
- Excess current.
- Potential hardware stress.
- Difficult debugging.

The tri-state design was successfully simulated, but it introduced an unnecessary electrical hazard for the physical prototype.

---

# 11. Final Routing Decision — 4:1 MUXes

The tri-state architecture was replaced by **4:1 multiplexers**.

Each LUT input gets one dedicated 4:1 MUX.

There are:

```text
4 LUTs × 3 inputs = 12 routing MUXes
```

Each routing MUX selects one of four sources:

```text
Source 0 ──┐
Source 1 ──┤
Source 2 ──┤──> 4:1 MUX ──> LUT input
Source 3 ──┘
             ^
             |
          2-bit select
```

### Why MUX routing won

| Property | Tri-state routing | 4:1 MUX routing |
|---|---|---|
| Source selection | Enable-based | Explicit |
| Contention risk | Possible | Eliminated |
| Debugging | More difficult | Easier |
| Configuration | Enable bits | 2-bit select |
| Behavior | Depends on exclusivity | Deterministic |
| Prototype suitability | Good | **Better** |

The key reason was **deterministic source selection without electrical contention**.

---

# 12. Routing Source Mapping

Each LUT input MUX has four possible sources.

### L0

```text
00 -> External
01 -> L1
10 -> L2
11 -> L3
```

### L1

```text
00 -> External
01 -> L0
10 -> L2
11 -> L3
```

### L2

```text
00 -> External
01 -> L0
10 -> L1
11 -> L3
```

### L3

```text
00 -> External
01 -> L0
10 -> L1
11 -> L2
```

Thus every LUT input can choose:

```text
external signal
OR
any other LUT output
```

---

# 13. Why Exclude a LUT's Own Output?

The own LUT output is deliberately excluded from its routing MUX.

Allowing:

```text
L0 output -> L0 input
```

could create combinational feedback:

```text
       +-------+
       |       |
       v       |
L0 -> MUX -> LUT
       ^       |
       +-------+
```

Depending on the function, this could result in:

- Oscillation.
- Undefined behavior.
- Timing-dependent operation.
- Ring-oscillator-like structures.
- Simulation convergence problems.

Version 1 is intended to be deterministic combinational logic, so self-feedback is prohibited.

Controlled feedback can be introduced later through explicit registers/DFFs.

---

# 14. External Inputs Are Routing Sources

The LUT itself does not distinguish between:

```text
external input
```

and:

```text
another LUT output
```

The LUT simply receives:

```text
A
B
C
```

The routing MUX determines what physical signal becomes each one.

Example:

```text
L2.A <- External A
L2.B <- L0
L2.C <- L3
```

This separation keeps the LUT completely generic.

---

# 15. Unused LUT Inputs

Unused LUT inputs must still be connected to a **defined logic source**.

They must never be electrically left floating.

For example:

```text
F = A & B
```

does not logically depend on C, but the physical C input still needs a defined value.

The truth table is therefore duplicated for both C states.

This gives:

```text
A & B = 88H
```

under the chosen LUT convention.

---

# 16. Routing Configuration Size

Each 4:1 MUX needs:

```text
2 select bits
```

There are:

```text
4 LUTs × 3 input MUXes = 12 MUXes
```

Therefore:

```text
12 × 2 = 24 routing bits
```

LUT configuration requires:

```text
4 × 8 = 32 bits
```

Total meaningful configuration:

```text
32 + 24 = 56 bits
```

---

# 17. Why Use 8 Bytes Instead of 56 Bits?

Although only 56 bits are meaningful, the physical configuration packet is rounded to:

```text
8 bytes = 64 bits
```

This gives a clean byte-oriented interface.

Proposed packing:

```text
Byte 0 -> L0 truth table
Byte 1 -> L1 truth table
Byte 2 -> L2 truth table
Byte 3 -> L3 truth table

Byte 4 -> L0 routing
Byte 5 -> L1 routing
Byte 6 -> L2 routing
Byte 7 -> L3 routing
```

Each routing byte:

```text
bits 1:0 -> input A select
bits 3:2 -> input B select
bits 5:4 -> input C select
bits 7:6 -> reserved
```

Reserved bits remain zero.

This makes the configuration packet easy for the STM32 to construct and transmit.

---

# 18. Serial Configuration Instead of Direct GPIO

Direct GPIO control would require a large number of STM32 pins.

The final architecture instead uses serial shift registers:

```text
STM32
 |
 +---- DATA
 |
 +---- CLOCK
 |
 +---- LATCH
 |
 v
SIPO shift-register chain
 |
 v
Configuration storage
 |
 v
LUT + routing fabric
```

### Advantages

- Very few STM32 pins.
- Scalable configuration interface.
- Simple firmware.
- Configuration represented naturally as a byte array.
- Fabric is less dependent on STM32 GPIO availability.

The complete configuration should be shifted first and the output latch pulsed only afterward, so the fabric can update in a controlled manner.

---

# 19. STM32 Role

The STM32 is **not the programmable logic fabric**.

It is the configuration and control processor.

The intended system is:

```text
User HDL-like command
        |
        v
STM32 parser
        |
        v
Logic synthesis
        |
        v
LUT mapping
        |
        v
Placement
        |
        v
Routing
        |
        v
Configuration bytes
        |
        v
SIPO
        |
        v
Physical fabric
```

The physical logic is implemented by the LUT and routing hardware.

The STM32 generates and loads the configuration.

---

# 20. Why Build a Small Compiler?

Manually entering:

```text
LUT truth-table bytes
+
routing selections
```

is useful for hardware testing, but it does not provide a meaningful programmable-logic experience.

The next abstraction is therefore a small Verilog-like command interface.

Example:

```text
input A B C D
output F
assign F = (A & B) ^ (C & D)
compile
```

The STM32 should then:

1. Parse the expression.
2. Build a logic representation.
3. Decompose it into LUT-sized functions.
4. Assign physical LUTs.
5. Generate truth-table bytes.
6. Generate routing configuration.
7. Pack the configuration.
8. Load the fabric.

This creates a tiny HDL-to-bitstream toolchain.

---

# 21. Why Not Implement Full Verilog?

A complete Verilog compiler is far beyond the required scope.

Instead, the project uses a small HDL-like language supporting:

```text
input
output
assign
&
|
^
!
'
()
```

Example:

```text
assign F = (A & B) ^ (C & D)
```

The objective is not Verilog compatibility.

The objective is to demonstrate:

```text
HDL
 ↓
Boolean logic
 ↓
LUT network
 ↓
Physical configuration
```

with a manageable embedded implementation.

---

# 22. Variable Count Is Not the Same as LUT Requirement

A function with more than three external variables is not automatically invalid.

Example:

```text
F = (A & B) ^ (C & D)
```

contains four external variables, but can be mapped to three LUTs:

```text
L0 = A & B
L1 = C & D
L2 = L0 ^ L1
```

Therefore the compiler must ultimately determine:

> Can the logic network be mapped onto at most four 3-input LUTs and the available routing topology?

rather than simply checking the number of external variables.

This distinction is fundamental to the compiler architecture.

---

# 23. Example: Boolean Decomposition

Consider:

```text
F = ABC + AB'C'
```

Factor:

```text
F = A(BC + B'C')
```

Recognize:

```text
BC + B'C' = B XNOR C
```

Therefore:

```text
D = B XNOR C
F = A & D
```

Physical implementation:

```text
L0 = B XNOR C
L1 = A & L0
```

Configuration:

```text
L0 = 99H
L1 = 88H
```

This demonstrates how multiple LUTs can implement a function that is not best treated as one LUT.

---

# 24. Full Adder as a Validation Target

A full adder is an excellent validation circuit because both required functions fit naturally into 3-input LUTs.

Sum:

```text
SUM = A ^ B ^ Cin
```

Configuration:

```text
96H
```

Carry:

```text
COUT = AB + AC + BC
```

Configuration:

```text
E8H
```

A multi-bit ripple-carry adder can then route the carry output of one stage into the next stage.

This validates both:

- LUT truth-table operation.
- Programmable inter-LUT routing.

---

# 25. Sequential Logic Deliberately Deferred

Version 1 contains no DFF/register stage.

This is intentional.

Adding sequential logic immediately would introduce:

- Clock distribution.
- Reset behavior.
- State storage.
- Timing concerns.
- Feedback.
- More complicated configuration semantics.

The current priority is to prove:

```text
LUT
+
Routing
+
Configuration
+
Compiler
```

for deterministic combinational designs.

Sequential logic will be a later architectural extension.

---

# 26. Final Hardware Trade-off Summary

| Decision | Alternative considered | Final choice | Main reason |
|---|---|---|---|
| LUT size | 2/4-input LUT | **3-input LUT** | Capability/complexity balance |
| LUT implementation | Gate network | **74HC151** | Direct truth-table lookup |
| LUT storage | Direct MCU GPIO | **74HC373** | Stable configuration storage |
| LUT count | Fewer/more LUTs | **4 LUTs** | Useful capacity without excessive complexity |
| Routing | Tri-state buffers | **4:1 MUXes** | No contention, deterministic |
| Self-routing | Allow own output | **Exclude** | Avoid combinational feedback |
| Configuration | Direct GPIO | **Serial SIPO** | Low MCU pin count |
| Config representation | 56-bit arbitrary stream | **8-byte packet** | Byte-aligned and simple |
| HDL | Full Verilog | **Small HDL-like syntax** | Appropriate scope |
| Sequential logic | Include in V1 | **Defer** | Keep V1 combinational |

# 28. Configuration Data Structure

The logical configuration can be represented as:

```c
typedef struct {
    uint8_t lut_config[4];
    uint8_t route_select[4][3];
} FPGA_Config;
```

Where:

```text
lut_config[i]
```

contains the truth table for LUT `i`.

And:

```text
route_select[i][j]
```

contains the 2-bit source selection for input `j` of LUT `i`.

This deliberately separates:

```text
LOGIC CONFIGURATION
```

from:

```text
ROUTING CONFIGURATION
```

which mirrors the physical architecture.

# 30. Design Philosophy

### 1. Prefer deterministic hardware

When two approaches provide similar functionality, prefer the one with fewer undefined electrical conditions.

This was the main reason MUX routing replaced tri-state routing.

### 2. Keep the programmable element conceptually pure

A LUT should implement:

```text
3 inputs -> arbitrary Boolean function
```

Routing should determine where those inputs come from.

### 3. Separate logic from configuration

The physical fabric should not depend on the internal implementation of the STM32.

The STM32 produces configuration; the fabric executes it.

### 4. Do not overbuild

The project intentionally does not attempt to reproduce a commercial FPGA architecture.

The goal is to demonstrate the fundamental FPGA concepts:

```text
Programmable Logic
+
Programmable Interconnect
+
Configuration Memory
+
Configuration Toolchain
```

### 5. Validate every abstraction layer independently

The intended validation order is:

```text
74HC151 LUT
       ↓
LUT configuration
       ↓
Routing MUX
       ↓
Multiple LUT composition
       ↓
Full fabric
       ↓
Serial configuration
       ↓
Compiler
```

This prevents compiler/software problems from being confused with hardware problems.

# 31. Final Architectural Statement

Version 1 is a:

> **4-LUT, 3-input, combinational programmable logic fabric with MUX-based programmable interconnect and serial configuration.**

Its core structure is:

```text
4 × 3-input LUTs
+
12 × 4:1 routing MUXes
+
LUT configuration latches
+
Serial configuration interface
+
STM32 configuration controller
```

The most important architectural decision was separating the programmable system into two layers:

```text
       +--------------------------+
       |       LUT LOGIC          |
       |     "What function?"     |
       +------------+-------------+
                    |
                    v
       +--------------------------+
       |    ROUTING NETWORK       |
       | "Which signal goes to    |
       |      which input?"       |
       +--------------------------+
```

Together, these form the programmable fabric.

# 33. Hardware Implementation Note

The logical LUT configuration convention documented here assumes the logical output polarity used during simulation and compiler generation.

Before final PCB/hardware integration, verify the exact **74HC151 output polarity and pin-level wiring**. If the selected physical implementation introduces an inversion, that inversion must be explicitly accounted for at the hardware-abstraction boundary.

The compiler's internal configuration convention should remain consistent regardless of the physical polarity.
